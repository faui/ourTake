# Jugnu private photo-memory contract

Last updated: 2026-07-14
Status: Slice 6 local/demo flow implemented

## Product truth

The manual event gallery is available to every signed event guest, including people who decline
optional photo matching. `Photos of you` is a deterministic fixture mapping for product rehearsal,
not face recognition, and every suggestion surface says `NOT AI FACE RECOGNITION`. No face image,
embedding, biometric vector, similarity model, or real provider is stored or invoked.

Real biometric processing, provider selection, processing location, processor terms, guardian legal
sufficiency, and production retention remain founder/legal gates.

## Private access boundary

- `event-media` is a private Supabase Storage bucket. Anonymous object download is denied.
- Gallery rows expose no public object URL. The product creates an HMAC view URL with event id, guest
  session id, media id, expiry, and signature.
- `/api/demo/media/[mediaId]` accepts only a non-expired, valid signature plus the same signed guest
  cookie and event. It returns `private, no-store` content.
- Seed gallery bytes are repo-created abstract SVG celebration illustrations generated by the route;
  they depict no real person and carry explicit source/license notes. A real uploaded object is read
  with the server service role only after the same guest-bound checks.
- The local fixture-session helper is disabled unless `JUGNU_DATA_ENV=local`.

## Upload and review lifecycle

1. The browser decodes the selected image, scales the longest side to at most 1280 px, and encodes
   WebP at quality 0.78. The original never leaves the browser.
2. The upload-ticket endpoint validates the event session, image type/size, and idempotency key, then
   creates or resumes an `upload_jobs` row and issues a two-minute HMAC upload URL.
3. The compressed blob stays in browser memory so the demonstrated first network interruption can be
   retried without silently choosing a different file or job.
4. A successful private object write creates a pending `media_items` row with dimensions, orientation,
   byte size, source/license notes, retention date, and uploader attribution. `complete` means upload
   complete and awaiting review; it does not mean published.
5. Moderator/ops publication or rejection requires an allowed role, human reason, current row version,
   and append-only `media_moderation_actions` plus audit history. A stale or sales-role action fails.

## Consent, minor, and guest controls

- Suggestions require a current granted `photo_matching` consent and an active event-local fixture
  profile. The profile contract requires `contains_biometric_vector=false`.
- A minor cannot create an active profile from their own session. The existing guardian linkage and
  consent controls remain conservative demo gates, not a claim of legal sufficiency.
- Claim/save and not-me are event/session scoped. Not-me is accepted only for an active suggestion.
- Forget-face immediately deactivates the fixture profile and writes a durable data request. Because
  no biometric vector exists, the UI says so plainly.
- A media deletion request must identify a visible event item. It enters human review and is never
  represented as immediate physical deletion.
- Manual gallery browsing remains available after decline, withdrawal, not-me, or forget.

## Rollback and production gate

Disable the memory surface and revoke the signing secret/bucket access without deleting data requests
or moderation history. Use only additive/compensating migrations. Any demo-asset purge needs a reviewed
seed cleanup. Passing local tests does not authorize production storage, real guest data, a biometric
provider, public deployment, or a production retention posture.
